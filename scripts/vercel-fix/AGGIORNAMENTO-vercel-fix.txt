ZoomZoom — Forzare Vercel a usare il nuovo schema (correzione definitiva)
====================================================================================

LA DIAGNOSI È CERTA (la tua diagnostica lo ha provato)
------------------------------------------------------
Sul server di Vercel la diagnostica ha letto, DENTRO la funzione che serve
il sito, il file prisma/schema.prisma: è AGGIORNATO (contiene province/
region/source). Eppure il client del database lì è VECCHIO.

Com'è possibile? Per come funziona Vercel: il client del database viene
generato UNA VOLTA, quando i pacchetti vengono installati durante una
build. Le build successive, se il file delle dipendenze (bun.lock) non è
cambiato, RIUSANO la cache di node_modules: niente reinstallazione,
niente rigenerazione. Il client era stato generato in una build fatta
quando lo schema era ancora vecchio; da allora Vercel lo ha conservato
nella cache e lo ha rifilato a ogni deploy, anche a quelli con lo schema
già aggiornato nel repo.

Ecco perché "bun run db:push" non poteva funzionare, per quante volte lo
hai eseguito: quel comando aggiorna il DATABASE (e il client del tuo
computer), non la cache di Vercel.

Il rimedio ha due mosse: una riga che rende la rigenerazione AUTOMATICA a
ogni build, e (se serve) la pulizia della cache con un redeploy forzato.

MOSSA 1 — LA RIGA PERMANENTE: "postinstall" (previene per sempre)
------------------------------------------------------------------
Nel package.json del progetto, dentro la sezione "scripts", aggiungi una
riga (è già pronta nel package.json di questo pacchetto):

    "postinstall": "prisma generate",

Così: ogni volta che Vercel installa i pacchetti (cioè a OGNI build),
rigenera il client del database partendo dal prisma/schema.prisma presente
nel repo — che è già aggiornato. È la prassi ufficiale Prisma per i
deploy su Vercel/serverless; senza questa riga il client nasce solo
quando la cache è vuota, ed è esattamente il buco in cui siete caduti.

ATTENZIONE prima di copiare il file: il package.json del pacchetto è
identico a quello del progetto, con la SOA riga in più. Se nel tempo hai
aggiunto tu altre dipendenze o script al tuo package.json, NON copiarlo
sopra: apri il tuo package.json e aggiungi a mano solo quella riga dentro
"scripts" (ricorda la virgola alla fine della riga precedente). Se invece
non lo hai mai toccato, copia pure il file del pacchetto.

MOSSA 2 — IL "FORZA" VERO: redeploy senza la vecchia cache
----------------------------------------------------------
La casella non si chiama "Clear Build Cache and Redeploy": il pannello
è stato rinnovato e l'opzione è al CONTRARIO. Nella finestra di Redeploy
c'è una casella

    "Use existing Build Cache"

che è GIA' SPUNTATA (riusa la cache vecchia): per la build pulita bisogna
TOGLIERE la spunta.

  1. apri  https://vercel.com  ed entra nel progetto del sito;
  2. scheda "Deployments" (in alto);
  3. clicca la deployment più recente (la prima dell'elenco);
  4. menu "..." (i tre puntini, in alto a destra) → "Redeploy";
  5. NELLA FINESTRA "Redeploy to Production" CHE SI APRE: TOGLI la spunta
     alla casella "Use existing Build Cache"
     (è questo che butta via la cache con il client vecchio: spunta =
     riusa la cache, niente spunta = build pulita);
  6. premi "Redeploy" e attendi 2-3 minuti la build (la vedi avanzare
     nella stessa pagina).

MOSSA 2-BIS — SE LA CASELLA NON SI TROVA (o l'errore resta): rimedio garantito, senza cache
--------------------------------------------------------------------------------------------
Se nella finestra non vedessi nessuna casella, o dopo il redeploy la
diagnostica dicesse ancora VECCHIO, c'è una strada che NON dipende dalla
cache: far rigenerare il client durante la BUILD, che viene eseguita
fresca dalla repository a ogni deploy, cache o non cache.

  1. su Vercel: entra nel progetto → scheda "Settings" → "General" →
     sezione "Build & Output Settings";
  2. alla voce "Build Command" attiva l'override e scrivi:
         prisma generate && next build
  3. premi "Save";
  4. torna in "Deployments" → ultima deployment → "..." → "Redeploy"
     (stavolta la casella della cache non conta: il comando di build si
     esegue comunque);
  5. verifica come sempre: https://TUO-SITO/api/diagnostica

Da qui in poi OGNI deploy rigenera il client dal prisma/schema.prisma
presente nella repository: il problema non può più ripetersi. (Esiste
anche la variabile d'ambiente VERCEL_FORCE_NO_BUILD_CACHE=1 che disattiva
la cache di build, ma il Build Command qui sopra è più mirato.)

SEQUENZA CONSIGLIATA (5 minuti in tutto)
----------------------------------------
1) Ferma il server di sviluppo locale (Ctrl+C) — non serve per Vercel,
   ma tienilo spento finché non hai finito, così nessun confonde le prove.
2) Copia il package.json del pacchetto nel progetto (o aggiungi a mano la
   riga "postinstall": "prisma generate" — vedi Mossa 1):
       Copy-Item -Force "C:\percorso\estratto\package.json" "C:\Users\Carlo\sito\zoomzoom\package.json"
3) Pubblica e rilascia:
       cd C:\Users\Carlo\sito\zoomzoom
       git add package.json
       git commit -m "rigenera il client del database a ogni build (postinstall)"
       git push
   Questo fa partire SUBITO una build nuova su Vercel (con il postinstall
   attivo). Attendi che compaia "Ready".
4) VERIFICA (la prova che decide tutto): apri nel browser
       https://TUO-SITO/api/diagnostica
   "clientDatabase" deve dire "aggiornato (conosce province/region/source)".
5) Se dice ancora VECCHIO: fai la Mossa 2 (Redeploy TOGLIENDO la spunta a
   "Use existing Build Cache") e ricontrolla /api/diagnostica; se la
casella non si trova o l'errore resta, la Mossa 2-BIS (Build Command
"prisma generate && next build") risolve in ogni caso.
6) Quando la diagnostica dice "aggiornato": riprova subito la recensione
   ("Aggiungi e Scrivi la Recensione") — questa volta la località viene
   salvata.

PERCHÉ QUESTA VOLTA È DIVERSO
-----------------------------
Le volte scorse il rimedio (db:push) agiva sul database e sul tuo
computer: giusto, ma non toccava la vera origine del problema, il client
congelato nella cache di Vercel. Ora si interviene esattamente lì: la
rigenerazione avviene DENTRO la build di Vercel, dallo schema che la
diagnostica ha confermato essere già aggiornato nel repo.

FILE DEL PACCHETTO
------------------
package.json — identico a quello del progetto, con la sola aggiunta di
                "postinstall": "prisma generate" negli script.
                (Se hai modifiche tue in package.json: aggiungi la riga
                a mano invece di copiare il file.)

Nessuna modifica a: schema del database, logica del sito, dipendenze,
variabili d'ambiente. Il database NON va toccato: è già aggiornato (la
diagnostica locale lo ha provato).

TEST ESEGUITI SU QUESTA VERSIONE
--------------------------------
- "bun run postinstall" eseguito: genera il client in meno di mezzo
  secondo e il client risultante contiene province/region/source
  (verificato a macchina sul file generato);
- la riga è compatibile con l'installazione locale su Windows (bun run
  install / bun install eseguono il postinstall del progetto sempre);
- nessun altro script toccato: dev, build, start, db:push ecc. restano
  identici.

SE DOPO LA MOSSA 2 DICESSE ANCORA VECCHIO
-----------------------------------------
Prima di tutto: fai la Mossa 2-BIS (Build Command "prisma generate &&
next build") — risolve sempre, perché il comando di build viene eseguito
dalla repository a ogni deploy e nessuna cache può saltarlo.

Solo se anche dopo la 2-BIS l'errore restasse (caso davvero remoto):
  1. apri su Vercel la deployment → "Building" / "Build Logs";
  2. cerca la riga "Generated Prisma Client" (deve esserci; se manca, il
     comando di build non è quello impostato: controlla di aver salvato
     l'override in Settings → General → Build & Output Settings);
  3. mandami quelle prime 20-30 righe dei Build Logs insieme alla risposta
     di /api/diagnostica: con quelle si vede al primo sguardo quale
     comando Vercel sta davvero eseguendo.

NOTA SULLA DIAGNOSTICA
----------------------
La pagina /api/diagnostica puoi lasciarla: è sola lettura, non espone
nessun dato degli utenti né segreti, e ti tornerà utile ai prossimi
aggiornamenti per verificare in un click che locale e pubblico siano
allineati. Se preferisci toglierla, basta eliminare il file
src/app/api/diagnostica/route.ts e rifare il deploy: nessun effetto.
